### Added

- A Ompiglet Binary can declare that it accepts overlay Ompiglets, so a custom base such as `ompig-tern` no longer needs a fused Ompiglet for every combination. Set `build.allowOverlays: true` in the Ompiglet you build (default off; like all of `build`, it is not inherited through `extends`), and its Binary takes `--ompiglet`, `OMPIG_OMPIGLET_PATH` and `OMPIG_OMPIGLET_NAME` as stock Ompig does: the selected Ompiglet resolves with the same project trust, Ompiglet directories and Package install flow, and merges onto the Binary's own Ompiglet as `extends` merges a child onto its base. An overlay can add extensions, skills and Packages, set `model`, narrow `tools` and strip more built-ins. It cannot replace or remove an extension or skill the Binary carries, set `slots.frontend` or `systemPrompt`, widen `tools`, `discovery`, `agentEnv` or an extension's `tools`, or re-enable a stripped built-in; each refusal names the field and the Binary, and a failed overlay never falls back to the Binary's own Ompiglet. The setting is part of the baked Ompiglet, so the Binary's signed Ompiglet digest covers it, and signature, closure and update checks are unchanged. A Binary built without the setting still refuses the selectors and now names the Binary and `build.allowOverlays` in the message. `/ompiglet` shows `Overlay of: <Binary>`, and `ompig ompiglet show` lists `allowOverlays`. Additive record D202.
